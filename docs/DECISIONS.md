# Decisions

One line per non-obvious technical decision, with the reason. Newest at the bottom.

| Date | Milestone | Decision | Why |
| --- | --- | --- | --- |
| 2026-10-27 | M0 | A ninth crate, `crates/onhold`, holds the single binary; `core-api` and `core-worker` are libraries. | The spec wants one binary for API and worker; neither library should depend on the other to provide `main`. |
| 2026-10-27 | M0 | Roles are subcommands (`onhold api`, `onhold worker`, `onhold migrate`) instead of a `--worker` flag. | Same binary and image as the spec asks; subcommands give each role its own typed options and leave room for `onhold admin …` (M8). |
| 2026-10-27 | M0 | Migrations run as a separate one-shot `onhold migrate` step, never on API start. | The spec requires migrations to run before the new version starts; doing it in-process would race when several API replicas boot. |
| 2026-10-27 | M0 | The pool connects lazily; `/healthz` never touches the database, `/readyz` does. | A database blip must make instances unready, not get every container restarted by the liveness probe. |
| 2026-10-27 | M0 | Integration tests use `#[sqlx::test]` (a fresh throwaway database per test on a real Postgres) instead of testcontainers. | Same guarantee (real Postgres, isolated per test) with no Docker-in-CI dependency; CI provides Postgres as a service container. Revisit if a test needs a different Postgres config. |
| 2026-10-27 | M0 | sqlx 0.9, axum 0.8, tower-http 0.7, Rust 1.97 pinned in `rust-toolchain.toml`. | Current stable releases at build time; the toolchain pin keeps CI, Docker and local builds identical. |
| 2026-10-27 | M0 | UUIDv7 ids are generated in Rust (`uuid` v7), not by a Postgres default. | Postgres 16 has no native `uuidv7()`; a single generator avoids two implementations disagreeing. |
| 2026-10-27 | M0 | `citext` and `pg_trgm` are enabled in the first migration. | Needed for case-insensitive emails/slugs (M1) and fuzzy search/dedup (M3); enabling extensions early keeps later migrations plain DDL. |
| 2026-10-27 | M0 | Logs are JSON by default (`LOG_FORMAT=pretty` for dev), with a `request_id` on every request span, generated or taken from `x-request-id` and echoed back. | The spec requires request ids on every log line; JSON is what log shippers ingest. `workspace_id` joins the span in M1. |
| 2026-10-27 | M0 | No frontend dependencies or CI steps yet; `web/` holds the agreed layout only. | Nothing to type-check until M1 generates the API client and M3 builds the shell; adding them earlier means maintaining unused deps. |
| 2026-10-27 | M1 | Rust 1.99.1 (from 1.97), with matching Docker base image; CI actions bumped to their current majors. | Current stable when M1 started; the toolchain file still keeps every build identical. |
| 2026-10-27 | M1 | The API pool runs every connection as `onhold_app` (`SET ROLE` on connect): no login, no `BYPASSRLS`, owns no tables. Migrations and operator tools use the login role. | Row-level security only binds roles that are not the table owner. With the app role always under policies, a missing `WHERE workspace_id` returns nothing instead of another tenant's rows. |
| 2026-10-27 | M1 | `onhold_app` is created idempotently and the down migration revokes its grants rather than dropping it. | Roles are cluster-wide; the throwaway per-test databases share one cluster and would fight over a drop. |
| 2026-10-27 | M1 | Workspace and user context travel as transaction-local settings (`app.workspace_id`, `app.user_id`) read by `app_workspace_id()` / `app_user_id()`. | `set_config(..., true)` dies with the transaction, so a pooled connection can never carry one request's tenant into the next. |
| 2026-10-27 | M1 | Pre-sign-in lookups (session by token hash, user by email, API key, invitation, magic link, OIDC identity) go through narrow `SECURITY DEFINER` functions that take one exact key and return one row. | Before authentication there is no context to satisfy a policy. Exact-key functions are the smallest hole that makes sign-in possible; none can list rows. |
| 2026-10-27 | M1 | The app role gets column-level `UPDATE` grants (not `users.is_superadmin`, `users.email`, `workspaces.slug/plan/plugin_slug`) and no `DELETE` on anything. `audit_log` is insert/select only. | Escalation and silent history edits are impossible from the API even with a bug in Rust; superadmin is granted only by `onhold admin superadmin grant`. Deletes are soft (`deleted_at`) per the spec. |
| 2026-10-27 | M1 | Services (business rules, authorisation, audit) live in `core-api/src/services`; handlers only translate HTTP. `core-db` holds queries only. | One `Ctx::authorize` call per operation in one layer; the worker and CLI call the same services. Moving them to their own crate is cheap later if the worker needs them without axum. |
| 2026-10-27 | M1 | Every change writes its audit row and its outbox event in the same transaction (`services::record`). The outbox table arrives now; delivery arrives with the worker in M2. | The spec's outbox guarantee holds from the first write; invitation and magic-link emails are queued as events today and sent once M2's mailer exists. Links go in the event, never in the audit log. |
| 2026-10-27 | M1 | Sessions are opaque 256-bit tokens in an `HttpOnly`, `SameSite=Lax` cookie, stored as SHA-256; writes with a cookie need the per-session `X-CSRF-Token`. API keys are `ohk_<id>_<secret>`, also stored hashed, scoped to a subset of their creator's permissions. | Revocable server-side (unlike JWTs), nothing usable is stored, and bearer keys need no CSRF protection because browsers never send them on their own. |
| 2026-10-27 | M1 | Passwords: Argon2id with the crate defaults, 12 to 256 characters, not equal to the email; 10 failures lock the account for 15 minutes. TOTP seeds are encrypted with AES-256-GCM bound to their user id, codes cannot be replayed, 10 single-use recovery codes. | OWASP's current guidance. A breached-password check and per-IP rate limiting need an external list and an edge proxy; both are deferred to M8's hardening pass. |
| 2026-10-27 | M1 | Secrets at rest use a keyring from `ENCRYPTION_KEYS` (`id:base64key,…`): the first key encrypts, every key decrypts. | Rotation without downtime: prepend a new key and new data uses it while old data still decrypts. A re-encryption command arrives with M8's operator tooling. |
| 2026-10-27 | M1 | There is no open sign-up. Accounts are created by accepting an invitation; workspaces are created by an operator (CLI or admin API) together with the owner's invitation. | The spec's onboarding is operator-led ("onboard a new client from CLI"). Self-serve sign-up can be added later without changing the model. |
| 2026-10-27 | M1 | One login can belong to many workspaces; requests name theirs with `X-Workspace-Id` (an API key implies its own). | The spec's open question, resolved with its own assumption; Solomon did not object. Agencies with several brands and freelancers working for several agencies both need it. |
| 2026-10-27 | M1 | An invitation can only be accepted by a signed-out new account or by the signed-in user with the same email. | Stops a forwarded invitation link from attaching a stranger's existing account. |
| 2026-10-27 | M1 | The `talent` role exists but cannot be assigned until M7. | Talent memberships are tied to a talent record, which arrives with the portal. |
| 2026-10-27 | M1 | Finance gets `billing:read` by default. | The spec gives Finance read access to everything outside its own area; billing details are the M1 piece of that. |
| 2026-10-27 | M1 | OIDC sign-in matches accounts by provider + subject first, then an invitation, then (Google only) a verified email. Microsoft's `email` is never used to match. | Microsoft lets any tenant admin set any address, verified or not (the "nOAuth" takeover). Multi-tenant Microsoft issuers are checked against the `login.microsoftonline.com/<tenant guid>/v2.0` pattern. |
| 2026-10-27 | M1 | The OIDC redirect URI is `<PUBLIC_BASE_URL>/api/v1/auth/oidc/<provider>/callback`: the API is served on the same origin as the web app. | Cookies stay first-party and `SameSite=Lax` works without CORS. The flow state rides in an encrypted, 10-minute cookie, so no table is needed. |
| 2026-10-27 | M1 | Superadmins need TOTP on and must have used it to sign in. Impersonation is per session, needs a reason, lasts at most an hour, and every row written meanwhile carries `impersonator_id`. | The spec's "every superadmin action is audited", made visible in the customer's own audit log. |
| 2026-10-27 | M1 | Writes accept `Idempotency-Key` (scoped to the credential, 24 hours, only successes stored). Records with a `version` column return it as an `ETag` and accept `If-Match`. | Seams for the offline desktop and mobile apps Solomon asked for: a queued write can be replayed safely, and a stale offline edit gets 412 instead of overwriting newer data. |
| 2026-10-27 | M1 | Workspace and actor ids are recorded on the request's log span. | Completes the M0 note: every log line inside a workspace request says which workspace and who. |
| 2026-10-27 | M1 | The OpenAPI document is committed at `web/packages/api-client/openapi.json`; a Rust test fails if it differs from the handlers, and CI fails if the generated TypeScript types differ from it. The client is `openapi-typescript` types plus `openapi-fetch`. | The spec's "the build fails if the spec changed and the client was not regenerated", in two cheap checks. pnpm and Node 22 enter the repo only for this package until M3. |
| 2026-10-27 | M1 | `argon2`, `blake2`, `rsa` and `num-bigint-dig` are optimised in dev builds. | Unoptimised Argon2 made every sign-in in tests take seconds; `rsa` only generates the mock identity provider's key in tests. |
| 2026-10-27 | M1 | `cargo audit` ignores RUSTSEC-2023-0071 (`rsa`) and RUSTSEC-2026-0387 (`crypto-bigint`), with reasons in `.cargo/audit.toml`. | Both are timing leaks in private-key arithmetic, reached only through `openidconnect`, which OnHold uses solely to verify signatures with public keys. Neither has a fix `openidconnect` can take yet; drop the ignores when it can. |
